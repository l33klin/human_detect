# 标注 RTSP 与前端验证

2026-10-21，在 pn41 验证。第一阶段按单路优先，不承诺两路同时达到 1080p/25 FPS。

新增两段 720p 监控视频、59.94 FPS 帧率元数据修复和 60 项回归测试的结果见 [后续复测](annotated-streams-cctv-validation.md)。下文保留首次验证的配置与测量记录。

## 环境与最终配置

- Ubuntu 22.04、Intel N6005、单块 PCIe Coral，沿用已有驱动。
- 普通用户 UID 10001、只读根文件系统的临时容器，映射 TPU 和 render 设备，补充数字组 1004、109。
- Python 3.9.25、PyAV 12.3.0、FFmpeg 5.1.9、iHD 23.1.1、TFLite Runtime 2.5.0.post1、MediaMTX 1.21.2。
- 原有独立编译模型与默认阈值，人体、人脸和身份特征推理均在 TPU，无 CPU 神经网络回退。
- 强制 VAAPI 解码、`h264_vaapi` 编码，CQP 24、无 B 帧。当前驱动仅支持 CQP；原生 Ubuntu FFmpeg 也通过了短时 CQP 编码探测。
- 标注流默认约 3 Hz 定期检测，逐帧跟踪，检测最大刷新间隔仍为 0.5 秒，身份缓存最长 1 秒。跟踪失败等情况允许提前完整推理。
- 独立写入线程、有界 4 包队列、无缓冲原生管道，减少封装写入对下一帧识别的阻塞。

所有视频均通过临时回环 RTSP 输入，不使用生产摄像头或已有身份库。结果是本次机器和场景下的观测，不是所有摄像头网络与画面的容量保证；没有测量端到端延迟或长时间稳定性。

## 性能

先预热并排空启动缓冲，再按两次计数差除以实际墙钟时间计算输出速率。不是模型 FPS，也没有用重复帧填充结果。

| 输入 | 实际测量窗口 | 平均提交编码 FPS | 输出 |
| --- | --- | --- | --- |
| 公开 Grace Hopper 静态人像生成的 1080p/25 FPS H.264/AAC | 30.14 秒 | 25.45 | 1920×1080 H.264 + Opus |
| 用户提供的家庭监控视频，768×432、30000/1001 FPS、无音轨 | 25.06 秒 | 28.93 | 768×432 H.264，无虚构音轨 |

第一行包含启动后缓冲收敛带来的轻微突发，不能理解为 25 FPS 输入产生了更多独立图像。额外读取输出 RTSP 约 3 秒，分别取得 73 个和 88 个视频包，时间戳按轨道递增，输出 H.264 无 B 帧。

1080p 有声样本在同一约 3 秒区间取得 150 个 Opus 包，音频包间隔小于 60 ms，验证了视频主动丢帧时音频仍保持连续。音频统一为 48 kHz 双声道；输入音频内容被转码，不保留原 AAC 编码字节。

保留的原始记录：[1080p 有声样本](validation/data/media-single-1080.json)、[真实视频](validation/data/media-cctv.json)。

真实视频原文件为 `istockphoto-482674813-640_adpp_is.mp4`，时长 21.054 秒、631 帧，H.264 Main，输入包含 B 帧。测试循环推流，未放大分辨率、未重编码输入。原文件 SHA-256：

```text
56c634e8064143b948ce3cf547ade75cf2107a93d7a2dc4bb0efcbfa13aa2f78
```

此前同步读写、5 Hz 定期检测的完整链路明显更慢。增加有界异步写入并将标注流的默认定期检测降至约 3 Hz 后达到上表结果；几个改动未做完全独立、随机交错的对照，不能将提升归因于某一项。JSON 模式默认 5 FPS 保持不变。

## 画面和识别观察

实际从输出 RTSP 解码画面检查：人体框、人脸框、中文身份文字都在视频像素中，位置与对应帧一致；框没有依靠前端单独叠加。文字按输出尺寸调整字号，靠近右边界时向内放置，避免整段身份文字落在画外。

在 1080p 参考样本的 147 次快照中，均检测到 1 个人、1 张脸并匹配参考身份。删除参考身份后，缓存匹配失效。该结果仅验证相同参考图的录入与匹配流程，不能作为陌生人误识率或实际摄像头准确率。

真实视频采集了 122 次快照：人体输出数为 2–5，其中 2 人 6 次、3 人 43 次、4 人 64 次、5 人 9 次；可见人脸输出数为 0–2。画面存在遮挡、侧脸、较小目标和水印，预览中有漏检及疑似重复框。这些数量是模型输出，不能作为实际人数；没有人工逐帧标注，因此不报告准确率。人物没有录入其真实身份，全部未匹配到参考身份，输出“未知”或“未检测到人脸”。

## 恢复、接口和前端

- 相同视频帧的编号、PTS、time_base、source_epoch 与识别结果共同流转，验证输出时间戳按轨道递增。
- 手动停止保留配置；重启服务后停止状态保持。运行中的流自动恢复，ID 和输出 RTSP 路径保持不变。
- 强杀采集进程后，私有进程组被回收，重建后 source_epoch 改变并恢复输出。
- 故障注入发现 `multiprocessing.Event` 在等待进程被强杀后可能使父进程 `set()` 卡住，已改为无锁共享字节和有界轮询。58 项测试覆盖强杀后删除及共享内存回收；另用真实视频完整重测恢复流程通过。
- 写入响应队列满时重建采集，不让管理线程退出后遗留一个假运行状态。
- WHEP 信令经应用同源代理，重写会话地址，支持创建及删除；API 密钥保护 API 和信令，前端静态资源可正常加载。
- 浏览器通过真实本地 MediaMTX/FFmpeg 链路验证播放、音视频轨道、添加/启停/删除流、身份录入/列表/删除。桌面和 390px 手机布局检查通过，无横向溢出。浏览器交互测试使用测试模型，不用于上述硬件性能或识别质量结论。

本地 Python 3.11 和服务器 Python 3.9 容器均通过 **58 项测试**；ruff 检查、格式检查、JavaScript 语法检查、Compose 合并校验和包含前端资源的 wheel 打包检查通过。

生产服务不写入原图、视频帧或录像。验证生成的少量预览仅作临时视觉检查，不提交到仓库；用户原始视频保持不变。临时验证服务和源进程完成后回收，生产部署按 [部署说明](annotated-streams.md)执行。
