# 运动触发、空场景降频与核显解码实测结果

2026-10-21，pn41，单块 PCIe TPU、N6005 核显。分支基于组合优化 `14d0df0`；初始基准 `e45854c`，I420 补测 `250493d`，前置筛帧补测 `5829591`。本地与 pn41 均通过 49 项测试，ruff 通过。

建议按场景开启运动触发＋空场景降频。核显单独开启没有优势；结合 RGB 转换前筛帧后，可明显降低解码 CPU 开销，完整识别链路相对同样筛帧的 CPU 对照只有少量额外耗时收益。默认配置未改，所有神经网络计算仍在 TPU，不存在 CPU DNN 回退。

## 运动与空场景对照

四组分别为原组合方案 combined、仅运动门控 motion（空画面最长 0.5 秒强制检测）、仅空场景降频 idle（2 秒，无运动唤醒）、motion_idle（运动唤醒＋2 秒强制检测）。原组合方案已经包含跟踪、身份缓存及两检测联合编译。

720p/1080p、5 个场景、60 帧、5 FPS 源时间戳、每组 3 轮，共 7,200 帧；预热 5 次，变体顺序随机。表内为全部帧合并平均耗时，单位 ms；正节省表示更快。

| 场景 | 宽×高 | combined | motion | idle | motion_idle | motion_idle 节省 |
| --- | --- | --- | --- | --- | --- | --- |
| 稳定空画面 | 1280×720 | 20.28 | 6.77 | 1.95 | 2.45 | +87.9% |
| 稳定空画面 | 1920×1080 | 20.54 | 7.20 | 2.11 | 2.70 | +86.9% |
| 进入/离开 | 1280×720 | 22.23 | 16.16 | 10.54 | 14.11 | +36.5% |
| 进入/离开 | 1920×1080 | 22.94 | 17.56 | 11.37 | 15.22 | +33.6% |
| 静止单人 | 1280×720 | 25.02 | 25.12 | 25.60 | 25.79 | -3.1% |
| 静止单人 | 1920×1080 | 26.25 | 27.13 | 26.68 | 26.93 | -2.6% |
| 缓慢淡入 | 1280×720 | 22.13 | 16.40 | 10.43 | 14.71 | +33.5% |
| 缓慢淡入 | 1920×1080 | 23.58 | 17.69 | 11.48 | 15.66 | +33.6% |
| 光照变化 | 1280×720 | 19.84 | 6.79 | 1.86 | 3.05 | +84.6% |
| 光照变化 | 1920×1080 | 20.50 | 7.20 | 2.03 | 3.34 | +83.7% |

1080p 稳定空画面，三轮人体 TPU 调用从 180 次降到 18 次，即减少 90%；平均处理耗时 20.54 → 2.70 ms，下降约 86.9%。P95 仅从 24.43 → 19.92 ms，原因是定期完整检测仍然存在，不能把平均提速理解为每帧都提速。静止有人时调用次数不变，门控增加约 2.6% 平均开销。

运动门控与 motion_idle 各 1,800 个配对帧，相对 combined 均没有额外/缺失正身份、配对身份差异、有人/无人帧差异；本次进入片段没有增加相对基线的发现延迟。仅 idle 组有 84 帧人体缺失、60 次正身份缺失，进入片段最多晚 1.4 秒发现。因此不建议只延长间隔而关闭运动唤醒。

这些是相对基线的公开合成素材对照，不是实际误识率或漏检率。缓慢淡入不是自然人物运动；弱变化、小目标、光影、镜头移动仍需真实摄像头调参。周期检测的保护期限按源时间计算；门控没有触发时可能到下次完整检测才发现人员。已有目标继续按原时序期限刷新，静止不会被直接删除。

## 真实 H.264 解码与 RGB 回传

testsrc2、25 FPS、每段 150 帧、三轮；统计包含进程启动、解码、RGB 处理和回传，CPU 时间含父进程及解码子进程。吞吐为回放处理能力，未按 25 FPS sleep。

| 输入 | 路径 | 解码回传 FPS | CPU ms/源帧 | 平均首帧 ms |
| --- | --- | --- | --- | --- |
| 1920×1080 | opencv | 158.90 | 13.20 | 47.31 |
| 1920×1080 | ffmpeg | 63.94 | 18.02 | 198.32 |
| 1920×1080 | vaapi | 33.84 | 30.68 | 151.62 |
| 1920×1080 | vaapi-i420 | 63.86 | 16.79 | 143.25 |
| 3840×2160 | opencv | 39.95 | 53.65 | 124.12 |
| 3840×2160 | ffmpeg | 17.50 | 68.19 | 265.36 |
| 3840×2160 | vaapi | 8.76 | 119.45 | 288.96 |
| 3840×2160 | vaapi-i420 | 17.31 | 63.38 | 243.82 |

OpenCV 使用库内 FFmpeg；外部 ffmpeg 控制组与核显后端使用同一 PPM/RGB 管道，线程策略及 FFmpeg 版本与 OpenCV 库内实现不同，因此分别报告。vaapi 强制硬件表面再下载 NV12；vaapi-i420 增加 CPU 平面重排，避开当前 FFmpeg 的慢速直接 NV12→RGB 路径。I420 不是核显 VPP 色彩转换。

未做前置筛帧时，初始 VAAPI 明显更慢。I420 后与外部 FFmpeg CPU 对照的吞吐接近，CPU 时间稍低；仍比原 OpenCV 慢且更耗 CPU。I420 是初测后单独补测，未与全部初始后端交错执行；表格是当前机器上的观测，不是统计置信结论。前置筛帧结果单列于后文。

GPU 缩放至 720p 的两个分辨率、三轮共 6 次均失败，保留错误记录，不回退软件；CPU 缩放控制组成功。单独 VPP 探测的 NV12 与 BGRA 路径都报 `Failed to create processing pipeline context`。只能确认当前驱动组合未跑通，不能据此认定核显硬件没有该能力。

## 分段定位

同一 1080p、150 帧 H.264，随机顺序重复三轮，输出到 `/dev/null`，不经过 Python RGB 管道。表中为平均整段墙钟和 CPU 时间，单位 ms。

| 路径 | 墙钟 ms | 子进程 CPU ms |
| --- | --- | --- |
| hardware_surfaces | 326.55 | 148.76 |
| nv12_download | 902.15 | 675.55 |
| nv12_rgb | 3848.91 | 3619.38 |
| i420_rgb | 1741.50 | 1516.46 |

核显解码并非主要耗时。加入下载、RGB 转换后开销增大；I420 布局变体改善了整段耗时，但完整回传仍未优于原采集。分段数字涉及不同输出与同步方式，不能将两个墙钟时间的差值当成精确、可相加的独立阶段耗时。完整命令见 conversion-profile.json。

## 解码＋TPU 整体回放

1080p H.264，空画面/进入离开/静止单人，各 150 个源帧；每 5 帧分析一次，相当于 5 FPS 源采样。四后端、两策略、三轮，共解码 10,800 帧、分析 2,160 帧。表内为平均整段耗时 ms，越低越好；包含解码及传输，不含网络。

| 场景 | 后端 | 原组合 | 加运动＋空场景降频 |
| --- | --- | --- | --- |
| 稳定空画面 | opencv | 1526.12 | 964.98 |
| 稳定空画面 | ffmpeg | 2226.22 | 1787.72 |
| 稳定空画面 | vaapi | 4460.96 | 4445.12 |
| 稳定空画面 | vaapi-i420 | 2682.35 | 2402.89 |
| 进入/离开 | opencv | 1679.67 | 1357.90 |
| 进入/离开 | ffmpeg | 2560.84 | 2368.39 |
| 进入/离开 | vaapi | 4635.71 | 4633.97 |
| 进入/离开 | vaapi-i420 | 2967.16 | 2852.34 |
| 静止单人 | opencv | 1874.38 | 1879.83 |
| 静止单人 | ffmpeg | 2910.22 | 2882.48 |
| 静止单人 | vaapi | 4845.93 | 4857.70 |
| 静止单人 | vaapi-i420 | 3353.70 | 3297.84 |

保留 OpenCV 时，空画面整体耗时 1,526 → 965 ms，下降约 36.8%；进入/离开 1,680 → 1,358 ms，下降约 19.2%；静止有人基本不变。相比纯 pipeline 的约 86.9% 空画面节省，完整回放收益更小，因为仍需解码全部源帧。GPU 路径的回传处理占主导，不能将门控与核显的独立指标相乘。服务默认 5 FPS 输出上限不会自动提高。

各后端内 motion_idle 相对 combined，以及核显后端相对同策略 FFmpeg CPU 对照，均未增加本次回放的人体有无差异、额外/缺失正身份或配对身份差异。初始 NV12/RGB 路径与 CPU 的像素摘要不同，部分身份模型调用次数也不同，不能当作完全相同像素/计算量的纯解码比较。I420 的稀疏像素摘要与 FFmpeg CPU 相同，但这不是全像素一致性证明。

## RGB 转换前筛帧：最终补测

前述路径将 25 FPS 源帧全部转为 RGB，再由服务挑选目标帧。最终改为在下载、RGB 转换和管道传输前先筛至 5 FPS。核显路径仍解码全部源帧，但每段 150 个源帧只回传 30 个 RGB 帧；增加相同筛帧方式的 FFmpeg CPU 控制组，分别随机顺序执行 3 轮。以下吞吐按源帧计算，不是识别输出 FPS。

| 输入 | 同样前置筛帧的后端 | 源帧处理 FPS | CPU ms/源帧 |
| --- | --- | --- | --- |
| 1920×1080 | FFmpeg CPU | 128.27 | 8.34 |
| 1920×1080 | VAAPI＋I420 | 202.09 | 4.21 |
| 3840×2160 | FFmpeg CPU | 33.86 | 31.70 |
| 3840×2160 | VAAPI＋I420 | 57.27 | 14.43 |

在这个相同筛帧的对照中，核显将 CPU 时间再降约 49.5% / 54.5%，整段解码回放耗时再降约 36.5% / 40.9%。这是筛帧之后的核显增量收益，不能把“少转换 80% 的 RGB 帧”也全部算给核显。上述筛帧、I420 布局调整都不是 GPU VPP；核显承担的是解码。

整体补测同样覆盖三个 1080p 场景、两策略、三轮，解码 5,400 个源帧、分析 1,080 帧。下表只比较 motion_idle 策略，平均每段 150 源帧耗时；CPU 列包含父/解码子进程。

| 场景 | CPU 前置筛帧 ms | 核显前置筛帧 ms | CPU 对照 ms/源帧 | 核显 ms/源帧 |
| --- | --- | --- | --- | --- |
| 稳定空画面 | 765.54 | 773.12 | 5.98 | 4.71 |
| 进入/离开 | 1138.53 | 1085.78 | 8.56 | 7.04 |
| 静止单人 | 1490.05 | 1452.81 | 10.83 | 9.73 |

完整识别中，核显相对同样筛帧的 CPU 路径平均耗时变化约为慢 1.0%、快 4.6%、快 2.5%；CPU 时间减少约 21.2%、17.8%、10.2%。因此当前核显的主要价值是腾出 CPU 资源，不能承诺单路识别速度翻倍。与前述 OpenCV＋motion_idle 相比，最终核显路径整段耗时低约 20%～23%，其中相当一部分来自前置筛帧。

筛帧补测相对同样筛帧的 CPU 对照，没有新增有人/无人帧差异、正身份增减或配对身份差异；相对同后端 combined，motion_idle 也没有增加这些差异或基线发现延迟。fps 过滤改变采样相位，不要求与初始每五帧取一帧逐像素相同，不能据此声称真实摄像头误识率不变。

最终服务中，外部 FFmpeg 后端均在转换前按该流的目标 fps 筛帧；`HD_CAPTURE_BACKEND=ffmpeg` 使用 CPU 解码，`vaapi-i420` 强制核显解码。原 OpenCV 后端不变。单路低负载可以先用 CPU 筛帧路径；多路或高分辨率时，核显路径值得做真实摄像头负载验证。默认仍为 OpenCV，不自动部署或切换。

## 实际视频 API 与硬件状态

- 回环 HTTP MPEG-TS 实时视频 → 采集子进程 → 真实 PCIe TPU → JSON：ffmpeg、vaapi、vaapi-i420 均通过，输出 1920×1080 并匹配已录入 Reference 身份。最终前置筛帧实现也重新通过这些验证。
- 删除流时采集线程、进程及 FFmpeg 子进程回收；另外验证先强制结束 VAAPI 采集父进程后，删除流仍能清理 FFmpeg。
- 指定不存在的核显设备时解码失败，没有软件解码回退；所有神经网络仍在 TPU。
- pn41：FFmpeg 4.4.2、Intel iHD 22.3.1、libva 2.14.0；SSH 用户未加入 render 组，测试只用临时 setpriv 权限，未改永久组成员。
- 当前 OpenCV OpenCL available/enabled 均为 false；没有验证核显光流、背景差分加速。
- 可选容器 overlay 的设备/GID 合并通过 Compose config 校验；本次未构建或验证容器内硬解码，也未部署常驻服务。

## 核显还能承担什么

硬件缩放和色彩转换最值得继续检查：如果能在核显上先缩小再回传，可能减少传输量及 CPU 转换。但本机现有 VPP 路径失败，暂没有可用提速结果；降分辨率还必须单独验证小人脸识别。Intel 驱动能力表列出了缩放与色彩转换：[Intel media-driver](https://github.com/intel/media-driver/blob/master/README.md)。

光流、背景差分可以另做 OpenCL 路径实验，但本机当前无可用 OpenCL 设备，低分辨率处理的上传下载也可能抵消收益。核显推理需要另一套模型和执行后端，不能直接执行现有 *_edgetpu.tflite；本分支继续保留 TPU 推理。
